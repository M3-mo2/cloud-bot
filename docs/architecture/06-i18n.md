# 06 — Internationalization (Arabic + English)

The bot is **bilingual from the foundation**: Arabic (`ar`, right-to-left) and
English (`en`, left-to-right). Localization is not a translation pass applied at
the end — every string-producing component takes a `Locale`, and the renderer,
keyboard builder, and formatters all receive it. This document defines how the
locale flows, how RTL is handled, and how formatting and plurals work.

---

## 1. The `Locale` type

```python
# core/locale.py
class Locale(str, Enum):
    AR = "ar"
    EN = "en"

def is_rtl(locale: Locale) -> bool:
    return locale is Locale.AR

LOCALE_LABELS = {
    Locale.AR: "العربية",
    Locale.EN: "English",
}
```

`Locale` is a plain enum in `core` so that `core`, `domain`, and `presentation`
can all use it without any dependency on aiogram or on the translation system.

---

## 2. Where the locale lives and how it flows

- **Persisted** in the `users` table (`locale` column), set at first `/start`,
  switchable later from Settings.
- **Resolved** once per update by `middleware/context.py` into
  `UserContext(tg_id, locale, is_admin, mode)`.
- **Injected** into handlers (`ctx.locale`), passed to services only when a
  service needs it (rare — e.g. an email-style template), and passed to **every**
  screen factory and the sender.
- **Never** stored in the FSM across a language switch without re-reading: if a
  user switches language mid-flow, the context's locale reflects the new value on
  the next update.

```
Update → context middleware → ctx.locale
       → service (domain data, locale-free)
       → screen(entity, ctx.locale) → RichDoc(locale) + markup(locale)
       → RichSender.send(... )   # build() sets is_rtl from locale
```

Domain entities contain **no** user-facing text. Only `presentation` turns an
entity into words, so there is exactly one place per string to translate.

## 3. The catalog

```python
# presentation/i18n/catalog.py
class Catalog:
    def t(self, key: str, locale: Locale, /, **args) -> str: ...
    def has(self, key: str, locale: Locale) -> bool: ...
```

Catalogs are plain modules with a `MESSAGES: dict[str, str]` (and a
`PLURALS: dict[str, dict[str, str]]` for count-sensitive keys):

```python
# catalogs/en.py
MESSAGES = {
    "ws.status.active": "Active",
    "ws.status.suspended": "Paused",
    "ws.status.locked": "Locked",
    "err.workspace_suspended": "This workspace is paused.",
    "run.status.exited": "Finished",
    "common.back": "Back",
    ...
}
PLURALS = {
    "count.workspaces": {"one": "{n} workspace", "other": "{n} workspaces"},
    ...
}
```

```python
# catalogs/ar.py
MESSAGES = {
    "ws.status.active": "نشِطة",
    "ws.status.suspended": "متوقفة مؤقتًا",
    "ws.status.locked": "مقفلة",
    "err.workspace_suspended": "هذه المساحة متوقفة مؤقتًا.",
    "run.status.exited": "انتهى بنجاح",
    "common.back": "رجوع",
    ...
}
PLURALS = {
    "count.workspaces": {"zero": "لا توجد مساحات", "one": "مساحة واحدة",
                          "two": "مساحتان", "few": "{n} مساحات",
                          "many": "{n} مساحة", "other": "{n} مساحة"},
    ...
}
```

Rules:
- **Key parity is tested.** A unit test fails if `en` and `ar` disagree on the key
  set; no screen can ship half-translated.
- **Keys are semantic**, never the English sentence (`err.workspace_suspended`,
  not `"This workspace is paused."`).
- **No string concatenation across keys** for sentences that vary by language;
  use placeholders in one key (`"{n} files in {ws}"` / word-order-safe Arabic).
- Missing key → renders `key` in DEV/DEBUG (loud) and a safe fallback + logged
  warning in PRODUCTION (never a crash, never raw).

## 4. The locale-to-language mapping of engine values

Engine values are translated through `presentation/mapping/`, not through the
catalog directly, so the mapping is testable in isolation:

```
engine error.code "workspace_suspended" → catalog key "err.workspace_suspended"
engine run.status "rate_limited"        → catalog key "run.status.rate_limited"
engine ws.status  "locked"              → catalog key "ws.status.locked"
```

The **complete** vocabulary (every code and status, AR + EN) is
[`../ui/05-errors-and-status.md`](../ui/05-errors-and-status.md). A test asserts
the mapping tables and the catalogs have identical key sets, so a newly added
engine code cannot silently fall through untranslated.

## 5. RTL and the rich messages

Arabic messages are sent with **`is_rtl=True`** — this is set **once**, in
`RichDoc.build()`, from `core.locale.is_rtl(locale)`:

```python
# presentation/rich/document.py
def build(self) -> InputRichMessage:
    return InputRichMessage(html=self._html, is_rtl=is_rtl(self._locale))
```

Every Arabic screen therefore renders with right-to-left paragraph direction,
right-aligned tables and lists, and correct punctuation placement — without any
per-screen work.

### 5.1 Mixed-direction text

RTL content that embeds LTR tokens (filenames, paths, code, identifiers, URLs) is
the classic failure case: `main.py` inside an Arabic sentence can visually
reorder. We handle it deliberately:

- **Code and paths are always in `<code>`/`<pre>`**, which the client renders in
  logical order independent of the surrounding direction. We never interpolate a
  raw identifier into flowing Arabic prose without wrapping it.
- **Inline LTR tokens** in prose are wrapped in `<code>` (or an explicit
  directional isolate where supported), e.g.:
  - EN: `Open file <code>main.py</code>`
  - AR: `افتح الملف <code>main.py</code>`
- **Paths** in breadcrumbs and headings are their own element, not embedded mid-
  sentence.

This is encoded in `presentation/rich/tags.py` helpers (`code()`, `path()`) so
screen authors get it right by default.

### 5.2 The direction of the language picker itself

The picker shows each language **in its own script** ("العربية", "English"),
regardless of the current UI locale, so a user who cannot read the current
language can still find their own. The picker is sent with the app default
direction (`is_rtl=False`) because it is inherently bilingual.

## 6. Numbers, digits, dates, and units

All numeric presentation goes through `presentation/i18n/formatters.py`; no screen
formats numbers itself.

| Formatter | EN example | AR example | Notes |
| --- | --- | --- | --- |
| `format_bytes` | `2.3 MB / 256 MB (1%)` | `٢٫٣ ميغابايت / ٢٥٦ ميغابايت (١٪)` | Binary-decimal prefix, Arabic-Indic digits for AR. |
| `format_duration` | `2m 05s` | `٢ د ٠٥ ث` | Human units, both languages. |
| `format_relative` | `2 minutes ago` | `قبل دقيقتين` | Uses `babel`; never an ISO timestamp. |
| `format_percent` | `3%` | `٣٪` | Compact fraction style. |
| `format_count` | pluralized | pluralized | Arabic six-form plural. |
| `format_datetime` | `3 Nov 2026, 20:41` | `٣ نوفمبر ٢٠٢٦، ٢٠:٤١` | Locale date order. |

Notes:
- **Arabic-Indic digits** are used for `ar` (via `babel`); identifiers such as
  workspace ids (`ws_...`) are **never** digit-localized — they stay ASCII and are
  shown in `<code>`.
- **Timestamps from the engine are UTC/RFC3339**; the bot renders them in the
  user's locale format directly (no timezone math promised beyond UTC in v1;
  noted in `DECISIONS`).
- **Byte figures** preserve the engine's honesty: `disk_complete:false` renders
  "≥ 2.3 MB" (a lower bound), matching SPEC §2.2's partial-list honesty.

## 7. Plurals

Count-sensitive strings use `Catalog.t` with a count argument and the locale's
plural category from `babel`:

```python
def pluralize(key: str, n: int, locale: Locale) -> str:
    form = babel_plural_category(locale, n)   # Arabic: zero/one/two/few/many/other
    return CATALOGS[locale].PLURALS[key][form].format(n=n)
```

Arabic's **six** categories (`zero, one, two, few, many, other`) are all authored
for every count key. A test renders each count key at `n ∈ {0,1,2,3,11,100}` for
both locales and snapshot-compares.

## 8. Language switching

- `/settings` → **🌐 Language / اللغة** → the picker.
- Switching edits the current message into the menu in the **new** locale (same
  message id), so the user sees the change immediately.
- The choice is persisted (`users.locale`); it survives restarts.
- Switching is available from the main menu at all times, and from the onboarding
  picker on first use.
- Any in-flight FSM prompt is re-rendered in the new locale on the next update
  (the FSM stores only state + minimal data, never rendered text).

```
⚙️ Settings / الإعدادات
[ 🌐 Language — English ]   (primary)
[ الرجوع — Back ]           (primary)
```

## 9. Testing i18n

1. **Key parity** — `en` ↔ `ar` key sets identical.
2. **Mapping coverage** — every engine code/status in the vocabulary has a
   catalog key in both languages (see `ui/05`).
3. **Golden screens** — every screen snapshot for AR and EN; AR snapshots assert
   `is_rtl=True` and the presence of Arabic strings; no snapshot may contain a raw
   engine token (e.g. `rate_limited`, `unprocessable`).
4. **Plural grid** — the `{0,1,2,3,11,100}` grid above, both locales.
5. **No-raw-output** — a test that runs every error/status through the mapping and
   asserts the output contains **no** engine code, **no** JSON braces, and **no**
   English engine `message`. DEBUG admin path excepted, asserted separately.

---

## 10. Adding a third language later

1. Add a member to `core/locale.py` and its label.
2. Add `catalogs/<lang>.py` (key-parity test forces completeness).
3. Add plural rules (babel already knows them).
4. Done — formatters, RTL flag, sender, and keyboards need no changes, because
   direction and formatting are derived from the `Locale`, not hardcoded per
   language.
